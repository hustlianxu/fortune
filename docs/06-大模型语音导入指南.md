# 大模型语音导入交易流水指南（v0.3.0）

> 对应用户需求："历史持仓太杂了，操作又多，有没有办法快速录入……跟大模型语音输入之后让他自动帮我导入，或者我在外部把语音转换成文字之后让大模型自动帮我导入"。

## 版本变更

| 版本 | 主要变更 |
|---|---|
| v0.2.1 | 初版：7 种基础类型（buy/sell/dividend/transfer_in/transfer_out/fee/interest），dry_run 预览 |
| v0.2.2 | 手续费可选 + 账户费率自动计算；product_type/exchange 自动补全 |
| **v0.3.0** | **类型扩展至 11 种**（新增 `ipo_win`/`stock_dividend`/`split`/`tax`）；新增 `ratio` 字段；批量导入分批并发避免超时；JSON 模式与自然语言模式完全对齐 |

## 一、使用场景

你有多笔历史交易要补录，手动逐条填写太繁琐。本功能允许你：
1. **方式 A（小程序内·自然语言）**：在「语音/文字录入」页直接粘贴一段自然语言文字（外部语音转文字后粘贴，或直接打字），大模型自动解析成结构化交易，确认后批量导入。
2. **方式 B（小程序内·JSON）**：在「语音/文字录入」页的「JSON 导入」tab，粘贴外部 LLM 已解析好的 JSON 数组，校验后批量导入。
3. **方式 C（外部 LLM）**：在任意 LLM 对话框（DeepSeek/ChatGPT/通义/MiMo）里用本文档提供的提示词，把语音转文字喂给 LLM，拿到 JSON 后再粘贴回小程序导入。

> **v0.3.0 起，自然语言模式与 JSON 模式行为完全一致**：同样的 11 种类型校验、同样的 ratio 字段、同样的 split/stock_dividend 特殊展示、同样的批量导入逻辑。两种模式只是入口不同——前者把"LLM 解析"步骤放在云函数里完成，后者由用户在外部 LLM 完成解析后直接提交 JSON。

## 二、方式 A：小程序内自然语言录入

### 2.1 入口
「我的」→「批量导入持仓」旁新增「语音/文字录入交易」入口 → `pages/import/voice`

### 2.2 操作流程
1. 选择目标账户（解析后的交易会挂到该账户；若文字中提到了账户名也可自动匹配）。
2. 在「自然语言」tab 文本框粘贴自然语言（支持多笔，一行一笔或自然段落均可）。
3. 点击「AI 解析预览」→ 调用 `parse_trades_by_text` 云函数（mode='text'），返回结构化交易数组。
4. 预览解析结果（可逐条编辑/删除/修正；split 类型会显示拆分比例输入框）。
5. 点击「确认导入」→ 云函数以 mode='json' 二次校验后，分批并发写入 `transactions` 集合并自动调用 `apply_transaction` 同步持仓。

## 三、方式 B / C：JSON 导入与外部 LLM 解析

### 3.2 返回 JSON 结构约定

```typescript
type TradeType =
  | 'buy'            // 买入
  | 'sell'           // 卖出
  | 'ipo_win'        // 打新中签（会计等同买入，会扣减账户余额）
  | 'dividend'       // 现金分红（有现金到账）
  | 'stock_dividend' // 红股入账/送股（只增份额，无现金流）
  | 'split'          // 份额拆分/合并（ratio>1 拆分，<1 合并）
  | 'tax'            // 纳税/扣税
  | 'transfer_in'    // 银证转入
  | 'transfer_out'   // 银证转出
  | 'fee'            // 手续费
  | 'interest';      // 利息

interface ParsedTrade {
  type: TradeType;
  product_name: string;   // 产品名称，如"招商银行"
  product_code: string;   // 产品代码，如"600036"；缺失填空串
  product_type?: string;  // 产品类型；可空，云函数会自动补全
  exchange?: string;      // 交易所（SH/SZ/HK/US）；可空，云函数会自动补全
  shares: number;         // 份额/数量；dividend/interest/split/tax/transfer_*/fee 填 0；stock_dividend 填红股股数
  price: number;          // 单价；非买卖类填 0
  fee: number;            // 手续费（元）；无则填 0，系统按账户费率自动计算
  amount: number;         // 交易金额（元）；buy/sell/ipo_win=shares×price，dividend=分红金额，tax=已扣税额；split/stock_dividend 填 0
  ratio: number;          // 拆分比例（仅 split 用）：1拆3 填 3，3合1 填 0.333；其他类型填 0
  trade_date: string;     // YYYY-MM-DD
  note: string;           // 备注，可空
}

// 云函数返回
interface ParseResult {
  success: boolean;
  trades: ParsedTrade[];
  warnings?: string[];    // 解析过程中的不确定项提示
  imported?: number;      // dry_run=false 时实际写入条数
  message?: string;
}
```

### 3.3 字段填写速查表

| type | shares | price | amount | fee | ratio | 说明 |
|---|---|---|---|---|---|---|
| buy | >0 | >0 | shares×price | 0或实际 | 0 | 买入，自动同步持仓成本 |
| sell | >0 | >0 | shares×price | 0或实际 | 0 | 卖出，自动同步持仓并实现盈亏 |
| ipo_win | >0 | >0(发行价) | shares×price | 0或实际 | 0 | 打新中签，会计等同买入 |
| dividend | 0 | 0 | 到账金额 | 0 | 0 | 现金分红，到账金额进账户余额 |
| stock_dividend | >0(红股数) | 0 | 0 | 0 | 0 | 送股/红股，只增份额，成本价摊薄 |
| split | 0 | 0 | 0 | 0 | >0(1拆3填3) / <1(3合1填0.333) | 份额拆分/合并，总资产不变 |
| tax | 0 | 0 | 已扣税额 | 0 | 0 | 纳税/扣税，从账户余额扣减 |
| transfer_in | 0 | 0 | 转入金额 | 0 | 0 | 银证转入，账户余额增加 |
| transfer_out | 0 | 0 | 转出金额 | 0 | 0 | 银证转出，账户余额减少 |
| fee | 0 | 0 | 手续费金额 | 0 | 0 | 单独登记手续费 |
| interest | 0 | 0 | 利息金额 | 0 | 0 | 利息到账，进账户余额 |

### 3.4 拿到 JSON 后
- 粘贴到小程序「语音/文字录入」页的「JSON 导入」tab，点击「AI 解析预览」校验后批量导入。
- 或直接用 JSON 调用 `parse_trades_by_text` 云函数的 `mode: 'json'` 模式导入。

## 四、云函数 `parse_trades_by_text` 接口

### 4.1 入参
```js
{
  text: string,        // 自然语言文本（mode='text' 时必填）
  json: string | ParsedTrade[],  // 已解析的 JSON（mode='json' 时必填，可字符串或对象数组）
  mode: 'text' | 'json',  // 默认 'text'
  account_id: string,  // 目标账户 ID（必填）
  provider?: string,   // LLM 提供商，默认取用户已配置且启用的第一个
  dry_run?: boolean,   // true=仅解析不写入，false=解析并写入（默认 true）
}
```

### 4.2 返回
```js
{
  success: boolean,
  trades: ParsedTrade[],   // 解析结果
  warnings: string[],
  imported: number,        // dry_run=false 时实际写入条数
  message?: string,
}
```

### 4.3 解析提示词（云函数内部使用）
云函数复用 `llm_gateway` 的 LLM 调用能力，使用上文 3.1 的提示词模板，temperature 设为 0 保证稳定输出。当前支持的全部 LLM provider：deepseek / qwen / glm / kimi / chatgpt / claude / bailian / mimo / minimax / custom。

### 4.4 写入校验（normalizeTrade）
单笔交易在写入前会经过 `normalizeTrade` 规整：
- type 不在 11 种枚举内 → 跳过并 warning
- buy/sell/ipo_win 缺 amount 但有 shares×price → 自动补全
- 日期格式异常 → 用今天兜底并 warning
- buy/sell/ipo_win/dividend/interest/stock_dividend/split 缺 product_code → warning（无法匹配持仓）
- split 缺 ratio 或 ratio ≤ 0 → warning
- stock_dividend 缺 shares 或 shares ≤ 0 → warning
- tax 缺 amount 或 amount ≤ 0 → warning

## 四点五、手续费：可选 + 账户费率自动计算（v0.2.2）

> 对应用户问题：「如果我帐户里面已经设置了各种手续费标准，那语音录入的时候还有必要说手续费吗？」

**结论：不用每次都说手续费。** 系统按以下优先级处理：

| 用户输入 | 处理方式 |
|---|---|
| 语音/文字明确提到手续费（如"花了5块手续费"） | 直接采用用户提供的值 |
| 未提到手续费（fee=0） | 调用 `utils/fee.js` 按目标账户的费率配置自动计算 |
| 账户未配置任何费率 | fee 保持为 0，与历史行为一致 |

### 4.5.1 自动计算口径（与同花顺一致）

**证券类（stock/etf/lof/hk_stock/us_stock）**

```
佣金 = max(成交金额 × 佣金率, 最低佣金)         // 沪市用 sh_*_rate，深市用 sz_*_rate
过户费 = 成交金额 × transfer_fee_rate           // 仅沪市，买卖双向
印花税 = 成交金额 × stamp_duty_rate             // 仅卖出

手续费 = 佣金 + 过户费(沪市) + 印花税(卖出)
```

**场外基金（fund_*）**

```
买入(申购) fee = max(金额 × subscription_fee_rate, subscription_fee_min)
卖出(赎回) fee = 金额 × redemption_fee_rate
```

### 4.5.2 product_type / exchange 的自动补全

为了让费率能正确匹配沪市/深市，云函数在解析后会自动补全：

1. **从已有持仓反查**：用 `product_code` 在该账户的 `holdings` 集合里查 `product_type`/`exchange`，命中则填入。
2. **代码前缀兜底推断**：
   - `60xxxx` / `68xxxx` / `51xxxx` / `50xxxx` → SH
   - `00xxxx` / `30xxxx` / `15xxxx` / `16xxxx` → SZ

### 4.5.3 透明可追溯

自动计算后会在 `warnings` 字段追加提示，预览页和导入完成提示都能看到，例如：

```
「招商银行」手续费由账户费率自动计算：¥5.12
「上证50ETF」手续费由账户费率自动计算：¥2.85
```

用户在预览页若觉得自动值不对，可手动编辑覆盖（手动录入页同款逻辑：手动改过就不再被自动覆盖）。

### 4.5.4 手动录入页同步支持

`pages/transactions/edit.js` 也接入了同一套费率计算器（`miniprogram/utils/fee.js`）：

- 选择账户、输入份额/单价后，手续费框留空时自动填充。
- 一旦用户手动修改手续费，标记为 `_feeTouched=true`，后续不再自动覆盖。
- 输入框下方有蓝色提示行：「按账户费率自动计算：¥X.XX（手动修改后将不再覆盖）」。

## 五、批量导入性能优化（v0.3.0 新增）

> 对应用户问题：「如果数据太多这个也会超时，如何解决时间过长又不想超时的问题。」

### 5.1 问题背景
微信小程序云函数单次调用默认超时 60 秒。若一次性导入 50+ 笔交易，按串行 `importTrade` 每笔内部还要调一次 `apply_transaction`，总耗时易突破 60s 上限，导致云函数被强制中断，已写入的数据无法回滚，体验很差。

### 5.2 解决方案：分批并发

云函数在确认导入阶段（`dry_run=false`）改为**分批并发**写入：

```js
const BATCH_SIZE = 5;
for (let i = 0; i < trades.length; i += BATCH_SIZE) {
  const batch = trades.slice(i, i + BATCH_SIZE);
  await Promise.all(batch.map((trade, j) =>
    importTrade(trade, account_id, warnings, openid)
      .then(() => { imported++; return true; })
      .catch(err => {
        warnings.push(`第 ${i + j + 1} 笔写入失败：${err.message}`);
        return false;
      })
  ));
}
```

- **BATCH_SIZE = 5**：经验值，单笔 apply_transaction 约 200~500ms，5 笔并发约 500ms 一批，50 笔约 5 秒，远低于 60s 上限。
- **失败隔离**：单笔写入失败只 warning，不阻断整批；返回结果里 `imported` 是实际成功条数，`warnings` 列出失败笔。
- **幂等保障**：写入前已做重复检测（同 `account_id + product_code + trade_date + amount` 跳过），即使重试也不会重复入账。

### 5.3 进一步优化建议（如需支持百笔以上）
若单次导入 200+ 笔仍超时，可考虑：
1. **前端分片提交**：前端按 50 笔一组多次调用云函数，每次 dry_run=false 写入一组。
2. **云函数超时配置**：在 `cloudfunctions/parse_trades_by_text/config.json` 中把 `timeout` 调到 60s 上限（微信云开发允许的最大值）。
3. **后台异步队列**：超大批量改用云函数 + 消息队列异步处理，前端轮询状态。

目前 v0.3.0 的分批并发方案已足够覆盖日常补录场景（50 笔以内无压力）。

## 六、容错与确认机制
- **dry_run 默认 true**：先解析预览，不直接写入，避免误操作。
- **warnings 字段**：对不确定的解析（如产品名无法匹配代码、日期模糊、split 缺 ratio 等）给出提示，用户在预览页可手动修正。
- **产品代码自动补全**：LLM 已被要求按产品名称从知识库反查代码；解析后云函数还会调用 `lookup_product` 二次校验。
- **重复检测**：导入前检查同 `account_id + product_code + trade_date + amount` 是否已存在，重复的标记跳过。
- **特殊类型预览展示**：split 显示「1拆3」/「3合1」而非金额；stock_dividend 显示「送 100 股」；编辑弹层对 split 类型额外提供「拆分比例」输入框。
